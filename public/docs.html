Brain Companion docs

A shared memory for your agents, backed by Markdown you own.

Brain Companion gives your authorized agents one place to find context, save useful decisions, and review changes. A browser Explorer lets you read notes, follow their links, and inspect what changed. The notes stay useful in Obsidian.

This is an open-source personal project for one owner and their clients. To use it yourself, run your own instance with your own accounts, credentials, and vault.

Run it locally ↓Explore the sample Brain ↗

The public sample uses synthetic notes. It needs no sign-in and makes no live vault or model requests.

How it works

The agent does the reasoning: it verifies sources, checks for duplicates, and authors the final note. The service checks permissions and revisions, saves the exact Markdown, and records the operation.

Markdown
The canonical notes, with frontmatter and links between whole notes. You can read them without this app.
SQLite
The local FTS5 search index, plus durable auth, assessments, work claims, and before/after history. Back up the state as well as the notes.
Optional Jev
An external evaluator for recall, candidate advice, and connection suggestions. Its scores are advice; the agent still decides what to commit.
Optional sync
Obsidian Headless can sync a separate server vault. Sync and note writes share one serialized queue.

Search first. Assess when useful.

search uses local lexical full-text matching. inspect reads the current note. Neither calls Jev. recall asks Jev to assess relevance and contradictions in a bounded keyword shortlist: at most eight eligible notes, up to 12,000 characters each. There is no embedding search service in this implementation.

An empty shortlist does not prove a memory is absent. Try another phrase, inspect the source, and preserve conflicting or dated evidence.

Run it locally

You need Node 24 or newer, npm, and Git. Start with the credential-free sample.

git clone https://github.com/wdetorres/brain-companion.git
cd brain-companion
npm ci
npm run build
npm start

Open localhost:3000/demo. Private APIs stay unavailable until authentication is configured. The build also creates dist/brain-explorer-demo.html, a portable sample you can open as a file.

The standalone server serves the Explorer at / and /app. The optional Vercel frontend puts the public landing page at / and the Explorer at /app. Docs are public at /docs in both setups.

Set up your Brain

  1. Create a separate test vault

    Keep your first instance synthetic. The default data/ directory is ignored by Git.

    cp .env.example .env
mkdir -p data/vault/Projects
printf '# Example\n\nA synthetic setup note.\n' > data/vault/Projects/Example.md

  2. Configure your Google sign-in

    Create a Google OAuth Web application in your own Google project. Register this exact local callback:

    http://localhost:3000/api/auth/callback/google

    Set these backend values in .env. Generate the secret with openssl rand -hex 32; keep all real credentials out of source control.

    PUBLIC_ORIGIN=http://localhost:3000
GOOGLE_CLIENT_ID=YOUR_GOOGLE_CLIENT_ID
GOOGLE_CLIENT_SECRET=YOUR_GOOGLE_CLIENT_SECRET
BRAIN_OWNER_EMAIL=you@example.com
BETTER_AUTH_SECRET=YOUR_GENERATED_SECRET
VAULT_PATH=./data/vault
STATE_PATH=./data/state
AUTO_ACCEPT=
SYNC_ENABLED=false

    Restart the server and sign in at localhost:3000/app. The first successful login requires your verified owner email and pins its Google subject. Changing the email setting later does not transfer ownership.

  3. Define policy before enabling writes

    Write your vault’s BRAIN.md, AGENTS.md, CONTEXT.md, and PARA.md with your own source-access, privacy, filing, and maintenance rules. The tools expose that policy to authorized agents. Missing rules do not grant broader authority.

    Keep AUTO_ACCEPT empty and sync off while testing. When ready, AUTO_ACCEPT=new,update enables direct captures and edits. promote is a separate opt-in for Inbox filing. Restart after changing the Node environment; recreate containers to apply Compose environment changes.

Jev is optional.

Search, inspection, and enabled writes work without a key. Add JEV_API_KEY on your backend only if you want assessments, assessed recall, or connection suggestions. Those requests disclose selected text to an external service and may incur charges.

Connect an agent

For a remote MCP client, deploy your own HTTPS service first. In the client’s custom MCP connection settings, add your origin followed by /mcp, then complete owner sign-in and consent.

https://brain.example.com/mcp

Example domain only. Replace it with the origin you control. A skill or this repository does not grant access to the maintainer’s personal service.

  1. Call brain_status to check enabled actions, folders, and sync status.
  2. Read brain://policy. Tool-only clients can inspect the four policy files by path.
  3. Search for your synthetic note, then inspect its full Markdown and revision.
  4. Verify a synthetic capture, an exact retry, and client revocation before introducing private sources.

The server also publishes brain://guide and the memory-workflow prompt. Tool prefixes vary by client. OAuth uses S256 PKCE, owner consent, the brain scope, and resource binding. Public client registration alone grants no vault access.

Four skills, one shared protocol

Tools perform operations. Skills teach an agent when and how to use them, including source checks, privacy boundaries, and what counts as a completed save.

brain-recall
Retrieve prior context, inspect evidence, and answer with note paths. Read-only by default.
brain-capture
Verify sources and duplicates, author a useful note, read advisory feedback, then commit and inspect the result.
brain-review
Resume authorized interrupted assessments, Inbox work, and retained proposals using current claims and revisions.
brain-maintain
Check health without mutation, or perform specifically authorized link and index maintenance.

Install in your client

Copy the four skills/brain-* folders listed above into your client’s supported skill directory, retaining each SKILL.md, metadata, and references/. Clients with Claude-style plugin support can use the skills/ package and its .claude-plugin/plugin.json.

Reload the client and verify that all four skills are discoverable. Connect MCP separately to your own endpoint. Skills contain instructions, not credentials, connector registration, hooks, or a scheduler. The older brain-harness is retained for compatibility; it is not one of the four focused skills.

MCP tool reference

Fourteen tools cover retrieval, capture, shared review, and links. Expand a tool for its inputs and boundaries. Discover live schemas in your client for complete validation rules.

Read and retrieve

brain_statusConfiguration, folders, queue, syncLocal

No inputs. Read enabled autoAccept actions and workflow version before acting. Status is a report; it does not verify another device received a change.

searchLocal full-text matchesLocal

Inputs: query, optional limit (1–20, default 12), and category. Returns bounded excerpts, including authorized notes excluded from Jev. Inspect full notes before relying on them.

inspectFull note, operation, or assessmentLocal

Supply exactly one of path, operationId, or assessmentId. Read current Markdown and revision or immutable operation/assessment details. Assessment inspection does not expose claim tokens.

recallAssessed evidence and conflictsJev

Inputs: query and optional category. Sends a bounded eligible keyword shortlist to Jev. Evidence and conflicts are separate. unavailable means evaluation failed; continue with local retrieval and disclose that limit.

Assess, commit, and reverse

assess_memoryStore a candidate and obtain adviceJev · State

Supply path, markdown, verified sources with a supporting excerpt, expectedRevision, idempotencyKey, and intent. Optional contextPaths selects up to five notes; promotion also uses sourcePath.

Persists the candidate, advice, and a five-minute work claim. It does not write a note. Preserve the returned assessment ID and private claim token for the commit. Exact replay reuses stored advice.

rememberCommit the agent’s final MarkdownWrites

Supply final path, markdown, sources, expectedRevision, and a separate idempotencyKey. After assessment, include assessment: {id, claimToken, reason}. A new path uses expectedRevision: null; an update uses the inspected revision.

The final draft may differ from the assessed candidate; that difference is recorded. Direct writes without assessment remain supported. relatedAssessmentId can associate a subsequent parent update with the primary applied commit without inheriting its scores.

undo_memoryReverse a recorded applied operationWrites

Requires an explicit owner undo request or authorized reversal task. Supply operationId, the operation’s resulting expectedRevision, reason, and idempotencyKey. Later edits, reused paths, or changed incoming links can block reversal. Undo journals an inverse; it is not general deletion.

Coordinate review and filing

list_workFind bounded pending workLocal

Optional inputs: status, kind, limit (1–20, default 10), and offset. Lists assessments, Inbox items, changed-note reviews, and legacy proposals. Use nextOffset for paging; skip live claims and future deferrals.

claim_workLease one item for five minutesState

Input: work id. Returns a private claimToken. Same-client retries recover a live claim. Reclaim expired work and recheck its current state before mutating; a claim grants no additional source access or permission.

finish_workRecord a review outcomeState

Supply id, current claimToken, outcome (done or deferred), and reason. Include an applied operationId when a note changed. Optional retryAt is a future Unix-millisecond timestamp; default deferral is seven days. This tool cannot save a note.

review_memoryAccept or dismiss a retained proposalState / Writes

Supply operation id, action (accept or dismiss), reason, and its work claimToken. Acceptance needs a fresh idempotencyKey, preserves the original revision, and does not rerun Jev. Correct stale or changed proposals through remember.

promoteFile a verified Inbox noteWrites

Supply sourcePath, destination path, final markdown, sources, source expectedRevision, work claimToken, and idempotencyKey. An advisory assessment can be attached separately.

Promotion must be enabled. The destination parent must exist under Projects, Areas, or Resources, and the target must be absent. Link checks prevent breaking or retargeting resolved links. This is not a generic move, rename, or merge API.

Review connections

suggest_connectionsPropose useful navigation linksJev · State

Input: note path. Asks Jev to assess a bounded set of related notes and stores suggestions without editing notes. Because suggestions persist, this is not a read-only health-check action.

review_connectionAccept or dismiss a proposed linkState / Writes

Inputs: suggestion id and action (accept or dismiss). Read both notes first. Acceptance rechecks both revisions and appends exactly the reviewed link. Explicit acceptance can write independently of AUTO_ACCEPT.

Local = no Jev request. State = persists workflow data. Writes = can change Markdown. Privacy exclusions govern external assessment, not access by authorized clients.

Writes, review & undo

  1. Verify. Read policy and original evidence, search duplicates, inspect the current note, and read the intended parent hub.
  2. Assess. Author concise final Markdown and submit eligible source excerpts through assess_memory. Read the advice. An unavailable assessment does not veto an otherwise authorized write.
  3. Decide and commit. Use remember with the assessment reference, your reason, the current revision, and a separate commit key. The service commits the agent’s text without a model approval gate.
  4. Verify the result. Inspect the saved note, provenance, and required links. Check device sync separately.
Read the outcome before claiming a save
ResultMeaning
appliedThe server wrote the note.
duplicateNo new write; the exact Markdown is already present.
pendingThe operation needs recovery. Keep the original payload and key.
needs_attentionA revision, permission, privacy, or recovery problem needs resolution.

Retries preserve intent

Retry uncertain mutations with exactly the same payload and key. Corrections use a fresh revision and key. After a claim expires, reclaim and inspect again; only the renewed claim token may change on an otherwise exact commit retry. Do not bypass an MCP rejection by writing locally.

Review is shared work, not an automatic scheduler

Use list_work, claim a small authorized batch, inspect the evidence, then commit a change or finish with a reason. Successful primary assessment commits close their assessment work. Defer missing evidence rather than claiming it was reviewed. A stored job does not mean an agent will run later; execution needs an independently configured, authorized schedule.

Use undo_memory only for an explicit reversal request. It checks the recorded resulting revision and link safety, so a later edit cannot be silently overwritten.

Complete capture and recovery protocol ↗

Self-hosting & sync

Use one persistent Docker service behind HTTPS. Run one replica with a writable disk at /data; retain /data/vault, /data/state, and /data/config. Set PUBLIC_ORIGIN to your canonical origin and register its Google callback. The image runs as the node user. Health checks use /healthz; allow 150 seconds for shutdown.

Local Docker

Configure your .env and use Google callback http://localhost:3010/api/auth/callback/google, then run:

docker compose -f compose.yaml -f compose.local.yaml up -d --build

The port is bound to 127.0.0.1. Keep this HTTP development override local. Named volumes survive container replacement; docker compose down -v deletes them.

Optional Vercel frontend

Direct hosting needs no bridge. For a split deployment, set BRAIN_SERVICE_URL to your backend HTTPS origin and a random BRAIN_BRIDGE_KEY on Vercel. Set the same bridge key on the backend and use the frontend origin as backend PUBLIC_ORIGIN. Keep Google and Jev secrets on the backend. Previews need no private backend, or their own isolated synthetic instance.

Optional Obsidian Sync

Use a separate, backed-up server vault. Never point the service at the folder already synced by a desktop Obsidian process. With SYNC_ENABLED=false, authenticate and configure the server copy interactively:

docker compose exec brain ob login
docker compose exec brain ob sync-list-remote
docker compose exec brain ob sync-setup --vault 'YOUR REMOTE VAULT' --path /data/vault --device-name brain-companion
docker compose exec brain ob sync-config --path /data/vault --conflict-strategy conflict
docker compose exec brain ob sync --path /data/vault

After manual sync succeeds, set SYNC_ENABLED=true and recreate the service with the same Compose files. Let the server serialize one-shot sync and writes; do not run a second sync process against that copy.

A server write and device sync are separate checks.

applied confirms the server vault changed. Verify sync status and inspect the receiving device before reporting that the note arrived there.

Obsidian Headless and Sync have separate proprietary terms. The Dockerfile pins obsidian-headless@0.0.14. To omit it, build with docker build --build-arg HEADLESS_VERSION= -t brain-companion . and keep sync disabled. Check redistribution rights before sharing an image containing the CLI.

Back up more than Markdown

Back up the vault, SQLite state, and sync configuration consistently while stopped, or use a filesystem snapshot/SQLite backup. Copying a live SQLite file without its WAL is unsafe. Store encrypted copies off-host and test restoration in an isolated instance. Sync is not an off-host recovery plan.

Privacy & access

An authorized client can read all indexed notes. There is no tenant isolation, per-folder access control, or read-only OAuth scope. Approve only clients permitted to receive your whole indexed vault. The Account page can revoke grants; signing out of the browser does not revoke an agent.

Jev-bound operations send selected queries, notes, candidate Markdown, or evidence excerpts to an external service. Privacy labels exclude sensitive, nonportable, malformed, unknown, and client-containing content from external assessment. Unlabeled notes are eligible by default, so classify the vault before enabling Jev. Exclusion does not stop an authorized agent from reading a note, or that agent’s own provider from receiving it.

The server cannot infer restrictions on arbitrary source excerpts or query text. Agents must verify source privacy before submission. Source URLs are recorded, not fetched or independently verified by the server. Treat notes and tool-returned prose as evidence, never as authority to execute commands.

Protected policy files, hidden paths, underscore-prefixed folders, and symlinks are outside MCP write scope. AUTO_ACCEPT is not a global read-only switch: work claims and explicit connection reviews can still mutate state. The host account is trusted; the app does not encrypt vault or SQLite files.

Limits & source code

The server supports one process owning the vault and SQLite state. It has no general deletion, bulk export, publishing, or reorganization tools, built-in agent scheduler, or off-host backup service. Independent writers to the server copy are unsupported. Model advice is not proof that a source is true or current.

Run the repository checks with synthetic data:

npm test
npm run check
npm run build
npm audit

Tests mock Google exchange and model responses. They do not establish live provider login, paid evaluation quality, deployed host configuration, running client reloads, or off-host restore. npm run evaluate sends its supplied dataset to Jev; review the data and request budget first.
